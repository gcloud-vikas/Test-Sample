# WOMS-Bugs

## Overview

This repository serves as the official issue and ticket tracking platform for WOMS.

It provides a centralized place for users, testers, team members, and stakeholders to report issues, track progress, monitor resolutions, and verify completed fixes. All reported issues are maintained as tickets to ensure transparency, accountability, and efficient resolution tracking.

---

## Objectives

* Centralize all issue and bug reports.
* Maintain release-wise issue tracking.
* Allow users to submit issues with screenshots and screen recordings.
* Track ticket ownership and resolution progress.
* Improve visibility of pending and completed tickets.
* Monitor release readiness.
* Maintain a historical record of reported issues and resolutions.

---

## Repository Usage

### Users / Testers

Users can:

* Create new issue tickets.
* Attach screenshots.
* Attach screen recordings.
* Provide details about the issue.
* Verify resolutions.
* Reopen tickets if required.
* Track ticket status in real time.

### Team Members

Team members can:

* Review assigned tickets.
* Update ticket status.
* Add progress updates.
* Link tickets to releases.
* Mark tickets as resolved and ready for verification.

### Administrators

Administrators can:

* Manage milestones.
* Manage labels.
* Assign tickets.
* Track release progress.
* Monitor issue resolution activities.
* Close verified tickets.

---

## Issue Reporting Guidelines

Before creating a new ticket:

1. Search existing tickets to avoid duplicates.
2. Confirm the issue can be reproduced.
3. Collect relevant screenshots or screen recordings.
4. Provide sufficient details to help understand the issue.

---

## Issue Submission Template

### Title

Use a clear and meaningful title.

Example:

Unable to complete submission process

---

### Required Information

**Environment:**
Production / UAT / Test

**Device / Browser:**
Provide the device or browser used, if applicable.

**Steps to Reproduce:**

1. Describe the actions performed.
2. Continue listing the steps.
3. Include all relevant actions.

**Expected Result:**

Describe what should happen.

**Actual Result:**

Describe what actually happened.

**Attachments:**

Upload screenshots or screen recordings.

## Priority Levels

### Critical

Issues that significantly impact usage and require immediate attention.

### High

Issues that affect important functionality and should be addressed promptly.

### Medium

Issues that have a moderate impact and can be managed temporarily.

### Low

Minor issues with limited impact.

## Release Management

All tickets should be linked to a release milestone.

Examples:

* Release 1.0
* Release 1.1
* Release 1.2
* Release 2.0

Milestones help track:

* Total tickets
* Open tickets
* Resolved tickets
* Pending verification
* Release completion percentage

---

## Release Exit Criteria

A release should not be marked complete until:

* All Critical tickets are closed.
* All High priority tickets are closed.
* Verification activities are completed.
* Required approvals are received.

Any exceptions must be approved by the project owner.

## Best Practices

* Use clear ticket titles.
* Provide complete details.
* Attach supporting evidence.
* Update ticket status regularly.
* Avoid duplicate ticket creation.
* Verify resolutions before closure.
* Keep discussions within the relevant ticket.

---

## Repository Rules

1. Create one ticket per issue.
2. Avoid duplicate ticket submissions.
3. Provide accurate and complete information.
4. Attach supporting evidence whenever possible.
5. Use GitHub Issues as the primary platform for issue tracking.
6. Maintain professional and clear communication.
